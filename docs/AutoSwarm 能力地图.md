# AutoSwarm 的 11 款 Agent：能力与“门”地图

Oct 23, 2026 · @Conway

## 结论速览

按“AutoSwarm 无界面调用时能否用上”来算，11 款 Agent 里只有两扇门是一家独有，其余的门集中在 Hermes、Nanobot、CodeBuddy 三家；Muse app 和 WorkBuddy 的不少门没有跟着过来。

- **只此一家的门很少**：主表里只剩一扇，即 AI 外呼电话（Hermes 的可选 `telephony` 技能，“部分”级）；腾讯云也不再是 CodeBuddy 独有，CloudBase 官方工具包同样点名 Claude Code、Codex 和 DeepSeek Harness。即时通讯分表里另有四扇：Hermes 的 Google Chat、LINE 对话渠道和 Telegram 读取（实验插件），以及 CodeBuddy 经腾讯文档官方 MCP 读微信账号下的在线文档。其余的门至少两家有，主表里的少数派集中在两处：X 实时数据（文档写明可用的只有 Hermes，Cursor 靠插件，Grok Build 只有源码证据）；模型生成视频（内置的只有 CodeBuddy 的 Kling V3 和 Hermes，Grok Build 待测）。
- **即时通讯：能对话的多，能读本人聊天记录的少。** 对话渠道上，Hermes 能在 16 个 IM 里的 15 个直接对话，nanobot 11 个，CodeBuddy 只有企业微信是“有”；编码类 Agent 要么只能在 Slack、Teams 里 @ 各家的云端产品，要么经飞书、钉钉的官方 CLI 接入，钉钉的 `dws dev connect` 还点名了 Claude Code、Codex、opencode 和 CodeBuddy。读本人聊天记录只有三条路：飞书 `lark-cli`、钉钉 `dws` 以用户身份读，11 款都能用；Slack、Teams 经厂商官方的 MCP 或各家的连接器；iMessage 读 Mac 本机的 `chat.db`。微信、企业微信、QQ、Discord、WhatsApp、Signal、LINE、Matrix 和 Messenger/Instagram 都读不到聊天记录。平台内的其他数据宽一些：企业微信、飞书、钉钉的官方 CLI 让 11 款都能以本人身份读写文档、日程、会议纪要、邮件和通讯录；微信只有腾讯文档的官方 MCP（只点名 CodeBuddy），小程序只对微信自己的 AI 开放，公众号没有官方入口。
- **各家手里的门差得很远。** 主表入口、生成、操作、自动化四类 24 行里（即时通讯另见分表），Hermes 有 19 行记“有”，Nanobot 13 行，CodeBuddy 8 行，其余 8 款各 3 到 6 行；Hermes、Nanobot 的门大多要常驻 gateway。其他几家各有看家门：Cursor 是唯一能经文档化 REST 接口无界面发起云端 agent 的，Claude Code 是唯一直接当 MCP 服务器的，Copilot 内置 GitHub MCP、手机远程控制已正式上线，Codex 的门多在 ChatGPT 连接器和桌面端。Muse Code、DSH、OpenCode 几乎没有自己的门，价值在模型和接口。
- **无界面驱动最省事的是 Grok Build 和 CodeBuddy**：JSON 事件流、JSON Schema 输出、ACP 和常驻服务都有。Claude Code、Codex、Muse Code 有 Schema 和 SDK，缺官方 ACP；Copilot、Cursor、OpenCode、Hermes、DSH 有 ACP，只给事件流。最费事的是 Nanobot，CLI 只出纯文本、没有 ACP。聊天和定时类的门，都要 AutoSwarm 另守一个常驻进程。
- **与旧六款地图的差别一：Meta 的门没有跟过来。** AutoSwarm 驱动的是 Muse Code，不是 Muse app。Instagram、Facebook、Meta 广告、WhatsApp、给商家打电话、Stripe Link 结账，都不属于 Muse Code。Meta 官方的 Ads MCP 和 WhatsApp Business MCP 点名支持 Claude Code、Codex、Cursor，名单里没有 Muse Code（[Meta MCP](https://developers.facebook.com/documentation/mcp)）。
- **差别二：腾讯的门只带过来一部分。** AutoSwarm 驱动的是 CodeBuddy，不是 WorkBuddy。据 CodeBuddy 自己的更新日志，WorkBuddy 以子进程托管同一个 CodeBuddy Code 引擎，两者共用账号和积分（[CodeBuddy 2.173.0 包](https://registry.npmjs.org/@tencent-ai/codebuddy-code/-/codebuddy-code-2.173.0.tgz)、[WorkBuddy 定价](https://www.workbuddy.cn/docs/workbuddy/Pricing)）。CodeBuddy 仍能直达个人微信（ClawBot）、微信客服、企业微信机器人和 Kling V3 视频，也能经微信下发任务；混元生图和公开分享链接只在国内版，微信支付只剩授权卡片，腾讯文档可经其官方 MCP 接入（点名 CodeBuddy）。QQ、飞书、钉钉、原生企业微信集成、微信支付插件和云端数字员工，都留在 WorkBuddy。
- **差别三：Hermes、Nanobot 和 Cursor 带来新门。** Hermes、Nanobot 带来旧图没有的聊天渠道门（QQ、飞书、钉钉、WhatsApp、Signal 等），外加来信即触发的邮件渠道。Cursor 的官方插件市场有 119 项，接通 X、飞书/Lark、Meta 广告、WhatsApp Business、Buffer 发帖和 Gmail 发信，旧图“Cursor 没有独有非代码门”的判断不再成立（[cursor/plugins](https://github.com/cursor/plugins/blob/main/.cursor-plugin/marketplace.json)）。另有三处改判：Grok Build 的 X 搜索从“未证实”变为源码可见；“本人已登录的浏览器”和“自身作 MCP 服务器”都不再是 Claude Code 独有。
- **对旧报告案例的影响**：案例 1 要的三扇门在 AutoSwarm 里都能补齐——X 由 Hermes 提供（Grok Build、Cursor 为备选），企业微信由 CodeBuddy 或 Hermes/Nanobot 提供，Gmail 来信触发改由 Hermes/Nanobot 的邮件渠道承担（Codex 的 Gmail 触发只在网页和手机端），腾讯文档则可由 CodeBuddy 经腾讯文档官方 MCP 接入；案例 3、4、6 用到的 Muse 电话、Stripe Link 结账、Instagram/Facebook/广告和 WhatsApp 全部失去，只能由 Hermes 的 `telephony` 与 `stripe-link-cli` 技能、Hermes/Nanobot 的 WhatsApp 渠道、Cursor/Codex/Claude Code 经 Meta 官方 Ads MCP 部分补位，Instagram、Facebook 主页的收发消息则找不到替代入口。

## 完整能力表

**图例**：有＝文档写明，AutoSwarm 经 CLI 或其他无界面接口驱动时可用；部分＝只经本产品官方插件、市场、预设或门的所有者点名支持的服务器，或只限部分版本或高档套餐，或只在图形界面、交互会话、网页、手机、云端产品，或属预览、Beta、实验功能；待测＝只有源码、二手来源，或文档只给交互入口、没说无界面能否用；无＝官方文档里找不到，或只能手工接任意第三方 MCP 服务器；独有＝全表该行只有这一家是“有”或“部分”。

上标数字对应第 4 节注释；“无”只表示所查官方文档里没有，不证明做不到；F 行用简写代替状态词（自家/多家/BYOK、MIT/闭源等）。A2–A4 即时通讯按产品拆成表后的三张分表。

**计数规则**

- 允许预先配好 key、登录或常驻进程（daemon、gateway、`serve`）。只因要订阅登录、要付费档或不能用 API key 不降级，登录方式的差别写进 F4。
- 产品自带并默认启用的技能按内置功能算；要另装的官方插件、可选技能、预设记“部分”。
- 模型可调用的工具，文档写明 CLI 可用、又没说仅限交互的，视为无界面可用。
- 一行含多项子能力时取最强的一项，覆盖范围写在注释里。
- B3、B5 是本机写代码产出的成品，能在无界面模式下写代码并执行就记“有”；A、C 两类对接外部服务的门，不按“自己写脚本也能连”计。门的所有者面向所有 AI Agent 发布的官方 CLI 不算自己写脚本：能在无界面模式下跑 shell 的 Agent，经它做到的记“部分”（如飞书 lark-cli、钉钉 dws），原生渠道仍记“有”；企业微信 wecom-cli 在消息上只能往机器人自己的会话里推送，不算对话，也读不到聊天记录，但经它读写文档、日程等其他数据同样记“部分”（表 3）；谷歌的 gws 自称不是官方支持的产品，不计入。
- 整款产品处于预览期（DSH）不逐格降级。

## 注释与待实测项

注释按上标编号排列。标“源码”“二手”“冲突”“推断”的条目证据最弱，都列进文末的实测清单。

1. 85) Signal：没有任何官方接口，Hermes（关联设备）和 nanobot（注册独立号码）都靠非官方的 signal-cli，只收新消息，没有历史或联系人工具；Signal 条款禁止自动发消息和自动注册账号（[Hermes Signal](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/messaging/signal.md)、[nanobot chat-apps](https://github.com/HKUDS/nanobot/blob/main/docs/chat-apps.md)、[Signal Terms](https://signal.org/legal/)）。
86) LINE：Messaging API 只能做官方账号机器人，没有消息历史接口，碰不到个人账号；LY 官方的 LINE Bot MCP（预览）只管推送和账号管理，README 只点名 Claude Desktop、Cline（[LINE Bot MCP Server](https://github.com/line/line-bot-mcp-server)）。11 款里只有 Hermes 内置 LINE 渠道，Webhook 要公网 HTTPS（[Hermes LINE](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/messaging/line.md)）。
87) Matrix：协议开放，用本人账号登录就能读历史，但 Hermes、nanobot 的渠道只处理新消息，没有会话列表或历史工具；Hermes 支持用本人账号接入（“机器人以你的身份发言”），会自动接受房间邀请、回复白名单里的所有私聊，用本人账号要谨慎（[Hermes Matrix](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/messaging/matrix.md)、[nanobot chat-apps](https://github.com/HKUDS/nanobot/blob/main/docs/chat-apps.md)）。
88) 两种情况不计入表 2。一是以本人账号接入的渠道：Hermes 的 WhatsApp 自聊和 Signal、Matrix 本人号模式，Claude Code、Hermes 的 iMessage，nanobot 的 WhatsApp 关联设备和 QQ NapCat，都能收到白名单联系人的新消息、以本人身份回复，但不给历史和会话列表。二是 Hermes 官方的 `mcp-serve` 插件：它把 Hermes 已连上的所有渠道暴露成 MCP 工具（列会话、读消息、等新事件、发消息），点名 Claude Code、Cursor、Codex 可当客户端，AutoSwarm 可借它让其他 Agent 经 Hermes 收发消息，但读到的只是 Hermes 机器人自己的对话（[mcp-serve](https://github.com/NousResearch/hermes-official-plugins/tree/main/mcp-serve)）。另外，飞书 `lark-cli`、钉钉 `dws` 都能以本人名义给任何人发消息，`dws event +listen-im --kind all-direct` 能实时收到本人的全部私聊，授权前要想清楚范围。
89) 微信（个人）其他数据：11 款能用的官方入口只有腾讯文档的远程 MCP（`docs.qq.com/openapi/mcp`）：用 QQ 或微信登录后在官网取个人令牌，就能列出、搜索本人的文档，读写文档、表格和智能表格，新建幻灯片、思维导图和流程图；免费用户每天 2,000 次调用。官方页面写的是“CodeBuddy / 其他 IDE”和 OpenClaw，11 款里只具体点名 CodeBuddy，所以 CodeBuddy 记“独有”；其余各家当通用 MCP 手工也能接，但没被点名，按图例记“无”。在微信小程序里建的腾讯文档存在同一账号下，按理也能读到，尚未实测（[腾讯文档 MCP](https://cloud.tencent.com/developer/mcp/server/11803)、[MCP 概述](https://docs.qq.com/open/document/mcp/)）。小程序 6 月 8 日起向“微信 AI 生态”开放：开发者开启后由平台读源码生成技能，或自己声明技能，通过评测和审核后只能被微信自己的 AI 调用，没有来源显示它对第三方 Agent 开放（[IT之家](https://www.ithome.com/0/961/614.htm)）；CloudBase MCP 读写的是开发者自己小程序的后端，属开发侧，见注释 19。公众号没有面向运营者的官方 MCP 或 CLI，只有社区实现；微信支付的 MCP 是让商户在智能体里加下单、查订单，不读用户账单；收藏、朋友圈、通讯录没有任何入口。
90) 企业微信其他数据：官方 `wecom-cli` 加一体化技能 `wecom-unified`：用户用企业微信扫码，把一个智能机器人绑定到自己名下（本人即“授权人”），之后 Agent 就能以本人身份查通讯录，收发邮件，读写文档、表格、智能表格和幻灯片，管理日程，查会议纪要和完整转写，管理待办和微盘。`wecom-unified` 点名 WorkBuddy、CodeBuddy、Codex、Cursor 等；首次扫码后可无界面运行（`--output-qrcode` 能把二维码存成图片），能跑 shell 的 Agent 都能用，所以 11 款都记“部分”（[wecom-unified](https://github.com/WecomTeam/wecom-unified)、[技能列表](https://github.com/WecomTeam/wecom-cli/blob/main/docs/skills.md)）。这就是 CodeBuddy 经授权拿到企业微信数据的办法，不是 CodeBuddy 独有；审批、打卡不在其中，聊天记录也没有。WorkBuddy 5.8.0 和企业微信 5.0.12 的深度集成（含“在企业授权范围内连接消息”）只在 WorkBuddy 里（[同花顺](https://stock.10jqka.com.cn/20261014/c680676327.shtml)）。注意两点：`wecom-cli` 默认会把调用它的 Agent 进程名和调用链上报给企业微信，要关得从源码构建；邮件技能展示预览后不等确认就发出，无人值守时会直接以授权人身份发信（[数据采集说明](https://github.com/WecomTeam/wecom-cli/blob/main/docs/data-collection.md)、[邮件技能](https://github.com/WecomTeam/wecom-cli/blob/main/skills/wecomcli-email/SKILL.md)）。
91) QQ 其他数据：QQ 机器人接口只看得到机器人所在频道和群里的内容，没有好友、群文件或 QQ 空间接口。CodeBuddy 记“部分”，靠腾讯文档官方 MCP（可用 QQ 登录，见注释 89）；Hermes 默认安装的 `himalaya` 邮箱技能和 nanobot 的邮件渠道走通用 IMAP，配上 QQ 邮箱的授权码就能用，但两家文档都没点名 QQ 邮箱；nanobot 只收新邮件，文档还建议给它单开一个邮箱（[Hermes himalaya](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/skills/bundled/email/email-himalaya.md)、[nanobot chat-apps](https://github.com/HKUDS/nanobot/blob/main/docs/chat-apps.md)）。腾讯官方的 QQ 邮箱连接器只在 WorkBuddy 里（[WorkBuddy 连接器](https://cloud.tencent.com/document/product/1831/134525)）。
92) 飞书其他数据：`lark-cli` 以用户身份覆盖文档、知识库、表格、多维表格、幻灯片、云空间、日历、会议纪要和妙记、邮件、审批、任务、OKR、考勤和通讯录，11 款都能用；Cursor 的官方飞书插件另能以授权用户身份处理文档、评论、文件和用户信息（[lark-cli](https://github.com/larksuite/cli)、[Cursor 飞书插件](https://github.com/cursor/plugins/blob/main/third_party/feishu/README.md)）。Hermes 自带的飞书文档工具用机器人身份，只在有人在文档评论里 @ 机器人时触发，不算（[Hermes Feishu](https://github.com/NousResearch/hermes-agent/blob/main/website/docs/user-guide/messaging/feishu.md)）。邮件、审批、OKR 等敏感权限要在开发者后台开通，企业租户可能还要管理员审批；以本人身份发信、处理审批属高风险写操作，`lark-cli` 会先要求确认。
93) 钉钉其他数据：`dws` 以用户身份覆盖 AI 表格、文档、钉盘、知识库、日历、AI 听记（摘要和完整转写）、邮箱、待办、审批、考勤、日志、通讯录和 DING，11 款都能用，企业管理员要先开通 CLI 访问（[dws 命令索引](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/blob/main/docs/command-index.md)）。DSH 官方连接器自带的 DWS 技能只含其中一部分（AI 表格、审批、考勤、日历、通讯录、DING、日志、待办、工作台和群管理），默认关闭；要用文档、钉盘、听记、邮箱和知识库，还得装完整的 `dws` 技能（[dws-cli 技能](https://github.com/DingTalk-Real-AI/dsh-dingtalk/blob/main/assets/skills/dws-cli/SKILL.md)）。
94) Slack 其他数据：Slack 官方 MCP 除消息外，还能列出本人所在的频道，并有 Canvas、列表、用户资料和文件的工具；Claude Code、Cursor 经 Slack 自家插件，Codex 经 OpenAI 的 Slack 插件都能用；Hermes、nanobot 的机器人只看得到所在频道，不算（[Slack MCP server](https://docs.slack.dev/ai/mcp-server)）。

### 上线前要实测的项

- [ ] **Cursor**：官方市场插件（X、Slack、飞书/Lark、Meta Ads、Gmail、Outlook、Teams、WhatsApp Business）在 `agent -p` 下能否加载并完成 OAuth，Cursor 自托管的 Teams、Outlook、WhatsApp 服务器尤其要测；X 插件是否要付费 X API。
- [ ] **Claude Code**：claude.ai 连接器和 Claude in Chrome 在 `claude -p` 下能否用（文档只说终端和 Agent SDK 会话会拉取连接器）；Channels（研究预览）在 `-p` 下的回传。
- [ ] **Codex**：ChatGPT 应用连接器（Gmail、Drive、Outlook 等）和 `$imagegen` 在 `codex exec` 下是否生效（源码不区分，文档未写）；`codex cloud exec` 只见于源码。
- [ ] **Grok Build**：`x_search`、`image_gen`、`image_to_video` 和 `/deep-research` 在 `grok -p` 下能否用；源码快照（09-29）比 v1.0.62 早约三周；用户档位有没有 Imagine 额度。
- [ ] **Hermes**：聊天、邮件、定时、webhook 都靠常驻 `hermes gateway`；不加 `--yolo` 时一次性运行遇到审批是拒绝还是卡住，文档没写。
- [ ] **Nanobot**：不开 gateway 时，`nanobot agent -m` 里的 `message` 工具能否送达；与 obot 同名的 `nanobot` 可执行文件可能冲突，宜写绝对路径（推断）。
- [ ] **CodeBuddy**：微信支付授权卡片在纯 `-p` 文本模式下如何呈现；国际版 ImageGen、Artifact 的远程开关；实验性 ComputerUse；标 Beta 的渠道与 HTTP API。
- [ ] **Muse Code**：`--contributor-mode off`（或 `MUSE_CONTRIBUTOR_MODE=0`）在每次 `muse exec` 和 `muse serve` 会话里是否生效；Computer Use 的系统范围；`/loop` 能否在 `muse serve` 里跑。
- [ ] **Copilot**：1.0.103 替换 `--remote` 的新参数名；电脑操控和 `/delegate` 在 `-p` 下能否用；Work IQ 能否发信。
- [ ] **DSH**：无界面运行的审批策略；实验插件（浏览器 attach、电脑操控、webhook）装进 headless profile 后是否接通；固定版本号（如 `@deepseek-ai/dsh@0.2.1-rc.2`）。
- [ ] **OpenCode**：V2 的 `run` 是否支持 JSON 输出和自动批准（文档未写）；V1、V2 共用 `opencode` 命令名，要固定一条线。
- [ ] **飞书、钉钉、企业微信 CLI**：在各家的无界面模式下实测 `lark-cli`、`dws`、`wecom-cli`。`codex exec` 的 `workspace-write` 沙箱默认不联网，要在配置里设 `[sandbox_workspace_write] network_access = true`（[Codex 安全与沙箱](https://learn.chatgpt.com/docs/agent-approvals-security.md)）；CodeBuddy 只从 `.codebuddy/skills` 加载技能；钉钉要管理员先开通 CLI 访问，三家首次授权都要扫码或设备码。
- [ ] **即时通讯分表**：Claude Code 装 Slack 官方插件后，在 `claude -p` 加 API key 下（先 `claude mcp login`）能否搜私信；`imessage` 插件的 `chat_messages` 不加 `--channels` 能否用；Codex 的 Slack、Teams 插件在 `codex exec` 下能否加载；Copilot 在已授权租户里用 Work IQ 读 Teams 聊天；`dws dev connect` 换掉默认的 Haiku、无工具、空目录配置后能否干正经活；`hermes send` 不开 gateway 能否发到微信、QQ、Google Chat；`wecom-cli message --help` 有没有服务端新下发的读取方法。
- [ ] **平台内数据**：腾讯文档官方 MCP（`docs.qq.com/openapi/mcp`，个人令牌）在 CodeBuddy 以外各家能否接通，微信小程序里建的文档能否读到；`wecom-cli` 的进程名上报要不要关（需从源码构建），邮件技能不等确认就发信，无人值守前要先限制；钉钉 `message list-all` 要的“消息搜索权益”是否已开通；Hermes `teams_pipeline` 的订阅续期任务有没有排上。
